# Пять опытов с проверкой ответа

Работай с новыми папками и копиями входа. Публичные исходники не должны содержать
твои реальные данные. Перед каждым опытом предскажи результат, затем проверь status/dead.

1. **Увеличь сумму.** Создай sample, до enqueue измени E0002 с 2000 на 4000.
   Выполни init → enqueue → work. Ожидается total_cents=19000, book=15000,
   pen=4000, done=3, dead=1. Дубль E0001 должен остаться дублем.
2. **Докажи атомарность партии.** После базового demo создай JSONL с новым E0005
   (bag,100) и изменённым E0001 (10001). enqueue должен дать exit 1. В status
   не появится E0005, сумма останется 17000. Порядок строк важен для проверки:
   сначала новая, потом конфликтная.
3. **Почини DLQ через политику.** В worker.CATEGORIES добавь toy. После demo
   вызови --db workspace/demo/queue.sqlite3 redrive E0004, затем work/status.
   Ожидается 4 done, 0 dead, total=20000, toy=3000. Если не менять правило,
   сообщение снова dead. Payload при redrive не переписывается.
4. **Проверь устаревший номер.** В отдельном тесте получи old=claim(now=1000),
   затем current=claim(now=1002). Попытка apply(old,now=1002) даёт LeaseLost и
   ноль эффектов; apply(current,now=1002) добавляет ровно один. Не обходи проверку
   generation. Сверь это с test_old_generation_cannot_complete_new_lease.
5. **Добавь метрику DLQ.** В snapshot вычисли max(attempts) по dead; для пустой
   DLQ выбери 0 через COALESCE. Базовое demo даёт 1. После трёх временных отказов
   одного события значение должно быть 3; после устранения причины и redrive
   оно исчезает из метрики dead. Добавь проверку обоих случаев.

Объясни словами: почему INSERT и ACK разделять опасно, почему expire в claim
не работает без запуска worker, зачем generation не сбрасывать при redrive,
какая часть гарантии сломается при замене локального INSERT на внешний HTTP?
